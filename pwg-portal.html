Developer integration notes

What's real, what's dummy, and what to wire up

This file is a static front-end prototype. All data lives in the DUMMY_DATA object at the top of the <script> block and every mutation (new client, new funding record, task checkbox, etc.) currently just updates that in-memory object and re-renders. Nothing persists on reload.

Suggested endpoints

GET/POST/PATCH  /api/clients
GET/POST/PATCH  /api/funding-records
GET/POST/PATCH  /api/fundability-audits
GET/POST/PATCH  /api/partners
GET/POST/PATCH  /api/tasks
GET             /api/activity
GET             /api/dashboard/summary
POST            /api/auth/login

Where to hook in

  • Every form's submit handler (submitNewClient, submitNewFunding, submitNewTask, submitNewPartner, submitAudit) — replace the array push with a POST, then re-render on success.
  • Kanban drag-to-stage is currently a dropdown-free click-to-open pattern; if you add real drag-and-drop, PATCH the client's stage on drop.
  • Task checkboxes call toggleTask(id) — swap for a PATCH.
  • KPI cards, funnel, and constraint charts are computed client-side in renderDashboard() from the same arrays — a real backend could instead expose a single /api/dashboard/summary.
  • Likely source of truth: GoHighLevel (CRM/pipeline) + Airtable (funding tracker, audits) — this UI assumes a unifying API layer in front of both.

Auth

No auth UI is built beyond the static user chip in the top bar — add a login screen and gate the app shell behind it.
